작업 중 규약·문서·절차에 물렸을 때 그 자리만 우회하지 않고 **규약 자체를 고치게 만드는** Claude Code
플러그인이다. 어떤 프로젝트(FE·BE·스크립트·문서)에도 설치해 쓸 수 있다. 절차는 도메인을 모르고,
프로젝트의 문서 지형은 설치 시 탐지해서 기록한다.

3원칙:

1. **규약은 얼어있지 않다.** 갭을 발견한 세션이, 같은 작업 단위 안에서, 사용자 지시를 기다리지 않고 고친다.
2. **증거 없으면 규약 없다.** 일반성(재발 지점을 실명으로 2개 이상)과 증거(측정값·실행 로그·`file:line`)가
   둘 다 있어야 규약화한다. 아니면 로컬에 남기거나 검증 후로 미룬다.
3. **문서에는 예산이 있다.** 규약은 가장 좁은 스코프에 쓰고, 넘치면 강등하거나 아카이브로 이관한다.
   무한히 자라는 규약 문서는 아무도 읽지 않는다.

> 정본은 영문 [`README.md`](README.md)이고, v0.5.0부터 독트린·스킬·에이전트 본문도 전부 영어다.
> 이 문서는 한국어 미러이며 내용이 갈리면 영문이 이긴다.
>
> **0.4.x에서 올라온다면**: 절차는 그대로이고 프로젝트 데이터 파일도 건드리지 않는다. 달라진 것은 둘이다.
> ① 보고 마커가 `self-improvement: N items`로 바뀌었다. 자체 마커를 이미 선언한 프로젝트는 그대로 쓴다.
> 요구되는 것은 그 «줄»이지 언어가 아니다. 다만 둘을 함께 선언해 두고 어느 쪽이 이기는지 안 적는 것은 안 된다.
> ② 업데이트 후 `/self-improvement:si-init`을 한 번 돌려라. 버전 스탬프를 대조해 옛 템플릿 문구만 보수하고,
> 라우팅 표·색인·로그·이관표는 그대로 둔다.
> 옛 한국어 용어를 상시 로드 문서에 적어 둔 설치본도 탐지에 그대로 걸리므로, 새로 만들지 않고 등록한다.

## 설치

```
/plugin marketplace add sh5623/self-improvement
/plugin install self-improvement@self-improvement
/reload-plugins
```

> [fe-rail](https://github.com/sh5623/fe-rail)이나 [parallel-worktree](https://github.com/sh5623/parallel-worktree)도 쓴다면 마켓 하나로 받을 수 있다: [`sh5623/guardrail`](https://github.com/sh5623/guardrail).

기본은 **user 스코프** 설치라 모든 프로젝트의 모든 세션에 적용된다. 한 레포로 한정하려면 `--scope project`,
끄려면 그 프로젝트 `.claude/settings.json`의 `enabledPlugins`에서 빼면 된다.

업데이트는 `/plugin marketplace update self-improvement` → `/reload-plugins` → 이미 세팅해 둔 프로젝트에서
**`/self-improvement:si-init` 재실행**이다. 업데이트는 도구를 바꾸지 데이터 파일을 바꾸지 않아서, 그 파일은
옛 템플릿이 준 문구를 그대로 들고 있다. 재실행은 버전 스탬프를 대조해 그 문구만 보수한다. 라우팅 값·색인·
로그는 건드리지 않는다.

![규약 갭이 게이트를 지나 가장 좁은 층으로 라우팅되는 흐름](docs/assets/loop.svg)

## 실제로 이렇게 보인다

사용자가 무언가를 호출하지 않는다. 다른 일을 하고 있는데, 세션이 나가는 길에 규약을 고친다.

```
$ claude
> transferStock 부분 커밋 버그 고쳐줘

  ✔ src/orders/OrderService.java:88
    두 번째 리포지토리 쓰기가 트랜잭션 경계 밖에서 돌고 있었다.

  마치기 전에: 이게 다른 데서도 재발하나?
    · PaymentService.java:141, SettlementService.java:52 — 같은 모양 (grep)
    · 증거: 운영 로그 + file:line              → 게이트 통과
    · 린터가 강제할 수 있다 → 문서가 아니라 도구 설정 층

  + src/test/java/arch/TransactionBoundaryTest.java   ArchUnit 룰
  + docs/conventions/CHANGELOG.md                     색인 1줄 + 로그 1블록

self-improvement: 1 item — ArchUnit rule (tool config layer) + changelog
```

마지막 줄 *self-improvement: 1 item*이 관측 가능한 신호다. 독트린이 리터럴 마커로 지정하므로 어느 언어로
일하든 그대로 나온다. **그 줄이 없으면 종료 자문을 건너뛴 것이고**, 되물어 복구할 수 있다. v0.5.0 이전에
자체 마커를 선언해 둔 프로젝트는 그대로 쓰면 된다. 요구되는 것은 그 «줄»이지 언어가 아니다.

## 구성

| 구성물 | 역할 |
|---|---|
| **SessionStart 훅** (`hooks/doctrine.md`) | 독트린 6조를 **매 세션** 컨텍스트에 주입한다. 물리면 규약을 고친다, 증거 게이트, 종료 자문, 보고 의무. compact 후에도 재주입되므로 긴 세션에서도 잊히지 않는다. |
| `/self-improvement:si-improve` | 프로토콜 본체: 감지 → 분류 → 검증 → 규약화 → 전파 → 기록 |
| `/self-improvement:si-init` | 프로젝트 부트스트랩(멱등): 문서 지형 탐지 → 데이터 파일 생성 → 상시 로드 문서에 포인터 3줄. 기존 시스템을 등록할 때도 실제 경로를 배선해 다음 세션이 다시 추론하지 않게 하고, 그 시스템에 이 플러그인의 표가 없으면 무엇이 각 표를 대신하는지 적은 **형식 맵**을 함께 남겨 다른 스킬이 계속 동작하게 한다. 플러그인 업데이트 후 재실행하면 버전 드리프트를 보수한다. |
| `/self-improvement:si-archive` | 비대·사문화 이관. 진입 조건이 둘로 독립돼 있다. 예산을 넘은 문서, 또는 누군가 지목한 사문화·중복 조항(이쪽은 예산과 무관) → 강등/병합/사문화 → 이관표 → changelog 로테이션 |
| `convention-smith` 에이전트 | 라우팅·초안이 애매할 때 위임한다. READ와 DRAFT만 하고, 게이트 판정과 최소 diff 초안을 돌려주며 적용은 호출자가 한다. |

플러그인은 버전 관리되는 **도구**다. 각 프로젝트에 남는 것은 **데이터 파일 1개**
(`docs/conventions/CHANGELOG.md`, 라우팅 표·예산·이관표·색인·로그를 담는다)와 상시 로드 문서의 포인터
3줄뿐이다. 플러그인을 업데이트해도 프로젝트가 쌓아 온 이력은 그대로다. 데이터 파일이 버전 스탬프를 들고
있는 이유도 그 분리에 있다. 그 파일이 생성될 때 받은 정형 문구는 절차보다 뒤처질 수 있고, `si-init`이
보수하는 것은 정확히 그 문구뿐이다.

## 동작 모델: 규약의 층과 이동 방향

새 규약은 **위에서부터 처음 맞는 층**에 쓴다(`si-improve` §4). 넘치거나 죽으면 **아래로만** 이동한다
(`si-archive`).

| 층 | 로드/발동 | 비고 |
|---|---|---|
| 도구 설정 (lint·format·type·test·CI) | 자동 강제 | 도구가 잡을 수 있으면 **문서 금지**. 문서 규약은 판단만 담는다 |
| 경로 스코프 룰 (`.claude/rules/*.md` + `paths:`) | 매칭 파일을 만질 때만 | 기본 안착지. 신규 파일이면 병렬 작업 충돌이 0이다 |
| 태스크·도메인 문서 (`docs/**`) | 해당 작업 시 명시적 Read | 플레이북·스펙 |
| 상시 로드 문서 (AGENTS.md/CLAUDE.md) | 모든 세션 | **≤200줄 예산.** 모든 세션·모든 파일에서 참인 것만 |
| 아카이브 (`docs/conventions/archive/`) | 로드 안 됨 | 사문화 규약과 로테이션된 로그. 삭제가 아니라 보존이라 "의도적 제거"와 "누락"이 구분된다 |

비대 관리 장치 3개:

- **로그 로테이션.** changelog 본문 블록은 15개 캡이다. 기록하는 사람이 그 자리에서 `grep -c '^### '`로
  검산하고 넘친 만큼 아카이브로 내린다. §색인과 §이관표는 전 기간 헤드에 남으므로 중복 확인이 파일 하나를
  훑는 것으로 끝난다.
- **이관표.** 층 이동이나 아카이브 1건마다 1행. 원문서에 개별 포인터를 남발하지 않고 표 하나가 옛 인용을
  커버한다.
- **캡은 그것을 실행할 절차 단계에 배선한다.** 문서 헤더에만 적지 않는다. 이건 이론이 아니다. 캡이 파일
  헤더에만 있어 아무 절차도 트리거하지 않은 탓에 로그가 42블록·949줄까지 자란 뒤에야 발견됐다.

## 빠른 시작

```
# 1) 프로젝트 최초 1회. 기존 유사 시스템이 있으면 그것을 등록하고 끝난다(덮어쓰지 않는다)
/self-improvement:si-init

# 2) 작업 중 규약에 물렸을 때 (또는 훅 독트린을 따라 세션이 스스로)
/self-improvement:si-improve  <무엇에 물렸는지 + 증거>

# 3) 규약 문서가 길어졌을 때
/self-improvement:si-archive
```

이후 모든 작업 보고 끝에 **`self-improvement: N items + where`** 또는 **`self-improvement: none`** 한 줄이
붙는 것이 정상 동작 신호다.

> **보장되는 것과 아닌 것.** 훅의 주입은 결정론적이라 독트린은 매 세션 반드시 컨텍스트에 들어간다.
> 그다음 행동은 지시 준수의 문제이지 강제가 아니고, 무시하는 세션을 차단하는 장치는 없다.
> 그래서 보고 라인이 존재한다. 그 줄이 없으면 종료 자문을 건너뛴 것이고, 되물어 복구할 수 있다.
>
> `Stop` 훅으로 누락을 차단할 수도 있지만 **의도적으로 넣지 않았다.** `Stop`은 **모든** 응답 종료에 발동해
> 작업 단위의 끝과 그 중간 턴을 구분하지 못한다. 중간 턴마다 줄을 요구하면 "해당 없음"이 양산되고 그 줄이
> 나르려던 신호가 죽는다. 한 프로젝트에서 굳혀야 하면 그 프로젝트의 완료 체크리스트에 칸으로 배선한다
> (`si-improve` §5).

## 효과가 있나

이 플러그인에 대한 근거는 두 종류이고, 각각 다른 질문에 답한다. 「이걸 쓴 팀이 버그를 몇 % 줄였다」는
없다. 그런 측정이 존재하지 않고, 없는 것을 지어내면 이 플러그인 자신의 증거 게이트를 깨는 것이다.

### 절차가 실제로 행동을 바꾸나

v0.2.0에서 규칙 3개(실패 유형 분류, 형태 매칭, 확정 전 효력 검증)를 추가할 때, 그 규칙들을
`si-improve` §4가 시키는 방식 그대로 검증했다. 격리된 픽스처 프로젝트에서 같은 갭 시나리오를
서브에이전트에 넘기되, 규칙이 있을 때와 없을 때를 나눠 돌렸다.

![변경 전 5회는 매번 실패를 재현했고, 변경 후 3회는 통과하며 같은 모양으로 수렴했다](docs/assets/does-it-work.svg)

중요한 것은 «수렴»이다. 5회가 서로 다른 5가지 모양을 냈다는 것은 문구가 안 먹혔다는 뜻이고, 3회가
일치했다는 것은 먹혔다는 뜻이다. 같은 방법을 통과하지 «못한» 후보 규칙이 2개 더 있는데, 이쪽이 더
쓸모 있는 결과다. 하나는 기존 독트린이 이미 3/3으로 잡고 있어 중복이었다. 다른 하나는 자기를 배선할
절차 단계가 없어, 위의 헤더 전용 캡과 똑같이 사문화될 운명이었다.

### 이 장치들이 없으면 얼마를 무나

예산 모델, 로그 로테이션, 이관표는 설계 취향이 아니다. 각각이 일반화 대상이던 프로젝트에서 실측된
사고 하나에 답한다.

![changelog가 캡 15에 대해 42블록까지 자랐고, 34KB 상시 로드 문서가 경로 스코프 룰 5개로 재편됐다](docs/assets/budget-overshoot.svg)

같은 프로젝트에서 나온 «문구» 쪽 사고 2건:

| 사고 | 실측 | 그래서 생긴 장치 |
|---|---|---|
| 판정 규칙에 무조건 단언을 씀 | 정상 케이스 **13건**을 결함으로 오검출 | 무조건 단언 금지. 규칙을 쓰기 전에 반례를 한 번 grep 한다 |
| 기록 단위가 「개선 1건」이라, 하루에 8건이 나온 날 | **색인 21줄, 본문 0개** | 작업 단위 1개가 로그 1블록. 본문은 안착 문서가 못 담는 것을 담는다 |

### 플러그인 자기 텍스트는 검증됐나

v0.4.0은 다른 모델이 이 플러그인의 텍스트를 읽고 file:line과 함께 결함 4건을 낸 데서 나왔다. 전부
픽스처로 재현한 뒤에 받아들였고, **제안된 수정 4개 중 2개는 그 검증에서 기각됐다.**

| 검증 대상 | 픽스처 | 결과 |
|---|---|---|
| README가 데이터 파일 후보로 통과하나 | 이 플러그인 README, 템플릿, 색인 없는 changelog, 평범한 README | 판별 grep **0 / 4 / 1 / 0** 히트. 설명 전용 문서는 배제된다 |
| `@AGENTS.md` import 판별용 엄격 정규식 | `CLAUDE.md` 3종: 맨줄, 백틱, 코드스팬 뒤 맨줄 | 엄격 정규식 **1/3 오판**. 평범한 grep에 명시 규칙을 더하면 **3/3** |

### 이 수치를 어떻게 읽나

**전부 한 프로젝트와 한 픽스처 세트에서 나왔다.** 유래 프로젝트는 레거시 마이그레이션과 API 연동을
거치며 규약 변경을 대략 40건 기록했고, 위 수치는 전부 그 이력이나 거기서 만든 픽스처로 거슬러 올라간다.
장치가 «무엇을 위한 것이고 어떻게 검증됐는지» 보이려고 공개한 것이지, 당신 레포에서 기대할 값이 아니다.
돌려 보고 다른 값이 나왔다면 그게 기여다. 이슈로 올려 달라.

## 실증 유래

아래 각 행은 실전 프로젝트(레거시 전환과 API 연동, 규약 개선 40여 건 기록)에서 실제로 일어난 사고와
그로부터 나온 규칙이다.

| 실사고 | 일반화된 규칙 |
|---|---|
| 자가개선이 "사용자가 시키면 하는 별도 작업"으로 취급돼 대부분 유실됨 | 자발 발동과 보고 의무. 그 줄이 없는 보고는 자문을 건너뛴 것이다 |
| 캡이 파일 헤더에만 있어 아무도 트리거하지 않음 → 로그 42블록·949줄 | 규칙은 그것을 실행할 절차 단계에 배선한다 |
| "합계는 항상 100" 무조건 단언이 정상 13건을 결함으로 오검출 | 무조건 단언 금지. 조건·예외를 명시하고, 쓰기 전 반례를 grep 한다 |
| "이건 우리 케이스만"으로 좁혔다가 다른 영역의 반례를 놓침 | 적용 범위를 **좁히는** 판정에도 근거가 필요하다 |
| 워밍된 캐시 수치로 "성능 해소"를 게시했다가 같은 날 철회 | 콜드 기준으로 잰다. 워밍된 수치는 하한이지 진실이 아니고, 상대방의 "고쳤다" 회신에도 같은 기준을 적용한다 |
| 상시 로드 규약 문서가 34KB가 되어 매 세션 비용을 치름 | 층 모델, 스코프 강등, 이관표 |
| 규약을 써 놓고 효력을 확인하지 않아, 선언만 하고 행동은 바꾸지 못하는 문구가 남음 | 확정 전에 문구를 검증한다. 방금 측정한 위반을 그 문장으로 다시 판정하고, 비용 큰 규약은 규약 없는 통제군과 대조한다 |
| 행동 지시에 "단, ~면 예외"가 붙어 규칙이 협상 대상이 됨 | 적용 범위는 구조로 한정하고, 진짜 예외는 분리된 줄의 조건식으로 쓴다 |
| 산출물 모양이 틀린 실패에 금지문을 씀. 그 유형에서는 역효과가 나는 형태다 | 실패 유형을 먼저 판정하고 그에 맞는 형태를 고른다 |
| 기록 단위가 "개선 1건"이라, 8건이 나온 날이 색인 21줄에 본문 0개로 끝났다. 블록마다 방금 규약이 안착한 문서의 복사본처럼 보였다 | 작업 단위 1개가 로그 1블록(개선 N건)이고 개선 1건이 색인 1줄이다. 본문은 안착 문서가 담지 못하는 것을 담는다: 계기·증거·검증 |
| 기존 규약 시스템을 "위치 보고"로 등록해 세션과 함께 사라졌다. 다음 세션은 같은 폴백 grep을 다시 돌렸고, 첫 후보는 README, 세 번째는 아카이브 파일이었다 | 등록은 상시 로드 문서에 실제 경로를 쓰고, 탐색은 그 선언을 가장 먼저 읽는다. 폴백 grep은 색인 표 보유를 요구하고 아카이브를 제외한다 |
| 플러그인 업데이트 후에도 데이터 파일이 옛 템플릿 규칙을 선언하고 있었고, 그것을 알아챌 방법이 없었다 | 데이터 파일의 버전 스탬프와 `si-init` 재실행 대조. 생성분은 정형 문구를 보수하고, 기존 시스템은 모순 보고까지만 한다 |
| §0이 데이터 파일 경로를 찾아 놓고도 그다음 명령이 전부 기본 경로를 타이핑했다. 기존 시스템이 다른 경로에 있는 프로젝트에서는 중복 검사와 로테이션 검산이 없는 파일을 읽었고, 없는 파일 grep은 0건으로 조용히 통과한다 | 경로는 §0에서 한 번 확정하고 이후 모든 명령이 `<datafile>`·`<archive>`를 치환한다. `ls`로 실재를 먼저 증명한다 |
| 포인터를 `AGENTS.md`에만 썼는데 Claude Code는 `CLAUDE.md`만 읽는다. 포인터가 로드되지 않아 다음 세션은 다시 grep으로 돌아갔다 | `AGENTS.md`에 쓰면 같은 단계에서 `CLAUDE.md`의 `@AGENTS.md` import(또는 심볼릭 링크)까지 보장하고, 보고에 실제 로드 경로를 적는다 |
| 기존 시스템 감지가 "self-improvement"라는 단어만 든 README를 후보로 돌려줬고 판별 근거가 없었다. 그것을 등록하면 데이터 파일 없이 셋업이 끝난다 | 후보를 내용으로 2단 판별한다. ① 색인·라우팅 표나 버전 스탬프 ② 표는 없어도 실제 기록을 담은 파일. 설명 전용 문서와 아카이브는 제외한다 |
| `si-init`은 표 없는 기존 시스템을 정본으로 등록하고 (옳게) 표를 강제 이식하지 않았는데, `si-improve`·`si-archive`·`convention-smith`는 그 파일에 없는 "§색인을 훑고" "§라우팅 표대로 라우팅"하려 했다. 등록은 성공했고 다음 개선은 거기서 멈췄다 | 등록이 선언에 **형식 맵**을 쓴다(색인·로그 단위·라우팅 표·아카이브를 무엇이 대신하는지. `none`도 정식 값이다). 모든 소비자가 그 맵을 읽고, 없는 헤딩을 grep 하는 대신 폴백 갈래를 탄다 |
| `si-archive`의 설명은 사문화·중복 조항 정리를 약속했는데 첫 단계가 "전부 예산 내면 종료"였다. 삭제된 기능의 규칙이 든 100줄짜리 문서는 분류 단계에 도달할 수 없었다 | 진입 트리거를 둘로 나눠 따로 잰다. 예산 초과, 또는 지목된 사문화·중복 조항. 후자는 명시적으로 예산에 묶이지 않는다 |

마지막 5행은 현장 사고가 아니라 이 플러그인 자체에 대한 교차 모델 리뷰에서 나왔다(v0.4.0에서 3건,
v0.6.0에서 2건). 각 건을 픽스처나 플러그인 자기 텍스트로 재현한 뒤 받아들였다.

## 요구 사항

Claude Code. 이게 전부다. 빌드 단계도, 런타임도, 설치할 의존성도 없다. 플러그인은 Markdown과 작은 JSON
파일 3개(매니페스트 2개 + 훅 설정 1개)이고, 프로젝트에 만드는 데이터 파일 하나도 Markdown이다.

## 이 플러그인 자체도 자가개선 대상

스킬·독트린·에이전트가 부족하면 같은 루프로 고친다. 이 레포를 수정하고 `.claude-plugin/plugin.json`의
`version`을 올린다. 메타 규약도 얼어있지 않다.

**절차를 고칠 때는 그 절차 자체를 검증한다.** v0.2.0에서 추가된 3개 규칙(실패 유형·형태 매칭·효력 검증)이
그 실례이고 수치는 [효과가 있나](#효과가-있나)에 있다. 규약 문구의 효력을 검증하라고 요구하는 문서가
스스로 미검증이면 그 요구에 설 자리가 없다.

v0.3.0은 반대 방향에서 왔다. 이 플러그인이 일반화된 그 프로젝트가 v0.2.0을 적용하다 역제안을 냈고, 각
주장을 픽스처로 재현한 뒤에 받아들였다. 폴백 탐색은 실제로 README를 첫 후보로, 아카이브 파일을 정본보다
위에 올렸고, 옛 기록 단위는 실제로 본문 없는 색인을 만들어 냈다.

v0.4.0은 세 번째 방향에서 왔다. 다른 모델이 이 플러그인의 텍스트를 리뷰해 결함 4건을 file:line과 함께
냈다. 전부 받기 전에 확인했고, 제안된 픽스 중 2건은 그 확인을 통과하지 못했다. 기존 시스템 후보에
"색인 표 보유"를 조건으로 걸면 색인이 없었을 뿐인 정상 규약 로그가 탈락하므로 판별을 2단으로 나눴다.
"`@AGENTS.md`가 정말 import 됐나"를 엄격 정규식으로 보면 인라인 코드 스팬 뒤에 온 bare import를 놓치므로,
단순 grep에 백틱 규칙 문장을 더하는 쪽으로 바꿨다. 네 번째 지적은 `Stop` 훅을 요구했고 근거 있는 거절로
답했다(위 [빠른 시작](#빠른-시작)의 인용문). 트리거를 관측할 수 없는 규칙은 규칙이 없는 것보다 나쁘다.

v0.6.0은 네 번째 리뷰에서 왔다. 이번에는 레포 두 개를 한꺼번에 본 리뷰였고, 여기에는 결함 2건을 냈다.
첫째는 스킬 사이의 이음새였다. `si-init`은 v0.4.0에서 색인·라우팅 표가 없는 기존 시스템을 받아들이게
됐는데, 그 등록을 소비하는 세 곳은 여전히 표를 전제해서 바로 다음 `si-improve`가 볼 곳이 없었다. 처방은
표를 붙이는 것이 아니라(v0.4.0이 그것을 거부한 것은 옳았다), 모든 소비자가 읽는 선언 한 줄짜리 **형식 맵**이고
`none`을 폴백 갈래로 보내는 정식 값으로 둔다. 둘째는 `si-archive` 안에서 설명과 첫 단계가 서로 모순된
것이고, 지금은 따로 재는 진입 트리거 둘이 됐다. 같은 릴리스에 GitHub Actions 워크플로를 넣어 매 푸시마다
모든 스킬·에이전트 frontmatter를 파싱하고 `claude plugin validate --strict`를 돌린다. 형제 레포가
description이 유효한 YAML이 아닌 스킬을 내보냈는데 아무것도 그걸 말해 주지 않았기 때문이다.

형태 매칭 표와 통제군 대조는 [obra/superpowers](https://github.com/obra/superpowers)의 `writing-skills`
메타스킬에서 왔다. 스킬 작성에 TDD를 적용해 압박 시나리오로 베이스라인을 잡고, 최소로 쓰고, 루프홀을
봉쇄하는 방식이다. 그쪽 head-to-head 워딩 실측이 "금지문은 산출물 형태 실패에 역효과이고, 예외 절 하나가
준수를 일관에서 불규칙으로 떨어뜨린다"를 보였고, 위 5회 베이스라인이 이 절차 안에서 그 두 실패를 그대로
재현했다.

이슈와 PR 환영한다. 변경을 어떻게 검증하는지는 [CONTRIBUTING](.github/CONTRIBUTING.md), 행동 규범은
[CODE_OF_CONDUCT](.github/CODE_OF_CONDUCT.md).
